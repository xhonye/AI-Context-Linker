# 业务资料完整性与时效修正

## 这轮要解决的问题

三问实测发现：遗漏已有执行规则会诱发重复开发建议；历史提交会被误当成当前功能；当前包只附带了生成器自身文档，业务项目仍缺正文。

## 实施顺序

1. Linker 标注既有配置提供的概述、状态、约束等字段。明确采集时间不是配置更新时间，配置与现行文档冲突时不得自行合并成事实。
2. 为已允许详细导出的项目选择已有允许清单里的 README/AGENTS，生成新私有配置和资料覆盖报告。保持 deny/summary-only 边界，不改历史配置、不上传原始事实 JSON。
3. SOL 增加显式项目级 README/AGENTS 随包正文，沿用自己的脱敏与事实哈希流程；历史提交、进展日志和计划明确标记为历史证据，不能据此证明当前实现。
4. 不以这次两个题目为采集白名单。验证业务项目中位于文档后部的条款能完整传递、历史内容不被标成当前状态、既有配置值保留但来源透明。
5. 运行现有测试、必要的新回归与打包验证；生成下一轮候选，逐行核对脱敏后的文档。保留第一次对比文件和回答复核记录。
6. 将新的候选放到单独的 Drive 对比目录并云端回读。更换业务细节题，线上独立会话验收后再判断替代，不用本地检查代替用户回答质量。

## 实现约束

不引入本地 AI、不自动判定历史文档的新旧、不清空人工配置、不改业务项目代码、不推送 Git。两套生成器独立采集，不能读取对方输出。

## 执行结果

已完成本轮工程改进。Linker 本地版本 0.2.3，配置来源标注随项目卡与切片提供；SOL 用 `--attach-document project/README.md` 精确指定文档，未选的同项目文件不会自动附上。

两边附文名单均为原允许范围内的 51 份文档。412 + 74 项测试、两套合成评测、安装后运行验证通过。两份新资料已上传到独立 Drive 对比目录并回读核对；旧版本与固定入口保留。SQL README 在两边采集完后出现后续改动，记录为快照后的源变化，本轮仍保留双方匹配的采集版本。

结果与两段业务问题提示词保留在仓库外的私有验证目录。用户已提供新版线上回答：业务细节基本打平，Linker 的引用更明确；仍有配置陈旧问题。后续自动回归发现先前对基线答案的一项证据不足评价有误，原始随包文档已支持该条款，已更正私有报告。题目和原生项目范围不同，不宣称替代验收完成。后续整理见 `2026-09-08-evidence-cleanup-plan.md`。
