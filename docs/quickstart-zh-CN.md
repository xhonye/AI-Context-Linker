# 中文使用说明：项目留本地，聊天有上下文

AI Context Linker 帮你准备一份经过核对的项目简报，让普通聊天能讨论
“今天做什么、卡在哪里、下一步是什么”。不需要把项目上传到 GitHub。

适用前提：你允许把**经过审阅的项目说明**交给在线聊天。
如果连项目名称、业务目标也不能离开电脑，就不要同步到 Drive 或在线聊天。
如果要求源码完全不出机，也不能让云端 AI 先看源码再总结。

## 先理解三个东西

如果你希望 Chat 有疑问时能直接看 README、AGENTS 的细节，可以在允许分享的项目配置中增加：

```json
"allow_files": ["README.md", "AGENTS.md"],
"attach_files": ["README.md", "AGENTS.md"]
```

这是项目配置中的两个字段，合并到已有配置中，保留原有 `allow_files` 项。生成并核对后，只需把完整的 **`ai_context.md`** 交给 Chat：总览、项目说明和选定文档正文都在里面。不要只交问题切片，它是节选版。整个过程不需要本地 AI。

带有脱敏标记的行未提供原文；没有选择的文件、链接网页和图片仍不在包内。文档太大或找不到时会明确报错。AGENTS 中的规则供了解项目使用，不是要求聊天照着执行。

| 东西 | 你需要知道的 | 放在哪里 |
|---|---|---|
| 本地项目 | 源码、运行数据和私人文件 | 原来的本地目录 |
| 私有草稿与核对单 | 还没批准的目标、卡点、下一步及版本指纹 | 仓库、同步目录之外 |
| 正式项目简报 | 只含你批准分享的事实与结构说明 | 独立的输出目录 |

“项目可被扫描”“行动状态已确认”“这份输出可同步”是三件不同的事。
生成 Markdown 不等于批准它。

## 日常怎样用：用中文说，不必手写 JSON

第一次只选一个项目。可以把下面这段话交给本地助手：

> 只处理我指定的项目，先核对已有的私有路径配置和可分享范围。
> 不扩大扫描范围，不读取原始聊天或全局记忆。
> 请用已有证据准备状态草稿和中文核对单，缺失项写未知。
> AI 建议单独标记，不作为我的决定；不要批准、上传或覆盖稳定入口。

你要确认的内容很少：

- **为什么现在做、当前目标**：这一次到底想解决什么。
- **卡点、下一步、完成标准**：真实缺什么；只做哪个动作；怎样算做完。
- **有效期、分享范围**：这些话到什么时候需要重新核对，哪些不能发到云端。

本地助手可以代填结构化草稿，核心编译器不调用模型、不理解自由对话。
你说“这条不对，改为……”之后，应先生成新核对单；修改后的版本不能继承旧批准。
已有更严格的逐字段批准条件时，以那些条件为准。

## 打开中文核对单

安装好仓库中的 CLI 后，可以先运行自带的**虚构项目示例**。
以下命令只写一个私有 Markdown，不会扫描真实项目，也不会批准或同步：

```powershell
python -m ai_context_linker preview-review-state `
  --manifest examples/synthetic-manifest-v02.json `
  --review-state examples/synthetic-review-state-v02.json `
  --project sample-project `
  --output "C:/Private/ai-context-linker/first-review.md"
```

真实项目使用你现有的私有 candidate manifest 和 review-state 文件替换示例输入。
最多显式选择三个项目；其他项目、工作区背景和关系不会被复制进核对单。
`summary-only` 或未明确允许详细信息的项目不能通过此入口恢复行动详情。

核对单会显示中文字段、未填写项、有效期、草稿原文和 SHA-256 文件指纹。
指纹用来指认版本，不是批准证明。英文原文不会自动翻译或改写。
时间有效性按输入 manifest 的时间判断，并在单据上注明；旧快照不是实时状态。

相同输入重复生成不会改写文件；输入变化时请用新的输出文件名。
核对单必须留在私有目录，不能放进仓库、已知同步目录或正式发布目录。
目录名检查不是通用云盘检测，你仍需确认目标目录实际上没有被同步。

## 确认后，才生成给聊天看的版本

1. 明确确认核对单对应的草稿版本、内容、用途和有效期。
2. 本地助手将获批状态接入现有私有配置，重新 `scan`。检查候选内容与变化。
3. 明确批准候选后，单独记录 `approve-snapshot`，再 `build` 或 `slice`。
4. 只把最终审阅过的 Markdown/项目分片交给聊天；私有配置、草稿、核对单和历史不交出去。

如果要放入现有 Drive 同步流程，只用专用输出文件夹。
不要同步项目目录、私有数据目录，也不要覆盖正在使用的 SOL 入口。
Linker 本身不负责连接或上传 Drive。

随后可以这样提问：

> 先读取我提供的这份项目简报，并说明它的更新时间。
> 今天最值得推进什么，为什么？目前卡在哪里，唯一下一步和完成标准是什么？
> 区分已确认事实、你的建议和未知。不要用提交数或文件数量替我决定优先级。
> 缺少批准状态时，只问最小必要的问题；不要猜测。

下一次更新时，再问“相比上一份批准快照变了什么？”
没有上一份批准快照，就只能建立基线，不能编造变化。

## 怎么知道它真的有用

先检查聊天是否答对目标、卡点、下一步、依赖与变化，以及有没有把已解决的问题重新说成阻塞。
同一真实项目至少观察两次更新。测试通过、文件更短或无路径命中，都不能代替这个检验。

当前不能给出一个可靠的“达到 SOL 多少百分比”。正式替代仍按
[既定评测合同](context-generation-evaluation-contract.md)验收，不能拿虚构示例或工程测试分数代替。
