# Chat High validation workflow

This is the default engineering-agent workflow for AI Context Linker and the private SOL Context baseline. The user authorized it after a successful fresh-Chat pair on 2026-09-08. It is not a network feature in either compiler.

## One useful iteration

1. Choose a small set of valuable changes. Read the nearest AGENTS and preserve existing work. Run proportionate local tests, compilation and packaging before online evaluation; do not repeat a successful full suite for a documentation-only closeout.
2. Prepare fresh private candidates independently from the permitted source surface. Use SOL `--no-sync`; use its actual project directory names for `--attach-document`, which may differ from Linker IDs. Neither generator consumes the other's output. No local AI analysis is required for this user's facts-and-documents workflow.
3. Capture within one observation window and check the shared document bodies, excluding explicit redaction differences. A material source change between captures invalidates the pair. Record capture times, artifact/fact hashes, scope and exclusions; distinguish native-product scope from a genuinely identical common surface.
4. Randomize neutral A/B filenames and a common top heading without changing facts. Keep the mapping private. Native formatting/content may still reveal clues, so do not claim perfect identity concealment.
5. Upload the reviewed Markdown files into a separate comparison folder, preserve stable entries and old rounds, then read both files back and compare their content. A transport error during creation/upload is ambiguous: inspect the target before retrying a mutation.
6. Open two fresh ordinary **Chat** conversations in the signed-in browser. Explicitly check Chat versus Work, the same model selection, and **High** in both menus. The validated UI displayed High as item 3 of 5 and Latest checked. Record the actual observed labels, not a presumed backend model. Prefer a named fixed model when specifically requested or when required for formal acceptance; if only Latest is observed, disclose that exact-model identity is unverified.
7. Use DOM semantic locators. If clicking is unreliable, focus the observed button/radio and activate it with the keyboard, then inspect state. Do not keep clicking old accessibility indices or screenshot coordinates. If an unrelated homepage suggestion is activated, stop it and discard that conversation from the pair.
8. Send the same question body with only the file link changed. Wait for the link to resolve to the intended file and for the send button to become enabled. Verify the visible message, selected High effort and two different new conversation URLs after sending. Do not send the mapping, expected answers, previous scores or the other conversation's answer.
9. Wait for completed answers with bounded, spaced status reads. The app can read final ordinary-Chat turns; its existing-conversation message API does not by itself verify or change the Chat model/effort. Avoid frequent unchanged polls.
10. Check actual file identity, capture time and fact hash where provided. An abbreviated hash is weaker identification and should be recorded as such; do not pretend the model returned a full value. Verify specific answers from the selected document versions, including English sections. Distinguish source-document assertions, inferred behavior and actual runtime verification. Do not count different placeholder words as behavioral contradictions without evidence.
11. Save a short result and only pursue the few highest-value findings. Keep raw prompts, answers, mappings, settings evidence, hashes and incidents outside Git. Preserve errors rather than overwriting them with a clean result. Public descriptions use separately reviewed anonymized aggregates, never raw private screenshots or business details.

## Questions and acceptance

For ordinary product checks, use one overview question and two concrete business-detail questions with source citations, explicit unknowns and a concise response limit. Freeze the questions before dispatch. A request to ignore previous chats does not prove account-level memory is disabled; record whether personalization was audited or left unchanged.

Workflow success means two verified fresh ordinary Chats at the requested setting actually read the intended artifacts and return reviewable final answers. It does not mean every answer is correct, every instruction was followed, or one generator has replaced the other.

Formal replacement acceptance still follows [the evaluation contract](context-generation-evaluation-contract.md): controlled model/state/surface, fixed questions and required repeated refresh/order checks. A native-scope pair, unknown backend model, or a single successful run cannot satisfy those gates by implication.

If browser control, login, High selection, upload/readback or Chat file access is unavailable, retain the completed local work, state the concrete blocker and provide the two exact prompts and files. Never substitute Work, a coding agent, a lower effort, stale files, or same-chat continuation while calling it a fresh High blind test.

Routine operation within the existing project permissions is authorized. Public GitHub publication, new data/permission scope, paid services, destructive operations and Git push retain their separate boundaries. No credentials or private runtime data enter the compiler or test prompts.

## Optional direct-repository control

When testing whether packaging helps more than direct source access, add a third fresh ordinary Chat at the same observed model selection and High effort. Give it only the approved public repository pinned to a verified full commit, permitting documents, source and tests inside that revision. Freeze the same question body and scoring criteria before dispatch; never tell it the expected winner.

Compare shared documented behavior separately from questions that require files absent from the packages. Keep version drift, redaction, input scope, retrieval failures, answer errors and runtime verification distinct. A frozen previous package may be reused after full cloud readback and a relevant-rule comparison against the pinned repository; do not present it as a fresh capture. Source types are visible, so this is not perfect source-blind judging.

A completed answer must actually exist: ordinary-Chat status reads can temporarily report an idle/completed user message before the assistant answer is available. Confirm the final assistant message or the visible completed answer rather than treating that status alone as success. Save API failures and mismatched snapshot identifiers explicitly.

The first three-way source-access trial favored direct repository reading on a source-only failure-path question; the shared business rules were broadly tied. This supports testing a small briefing plus on-demand source access, not expanding default source uploads, adding local AI analysis, or retiring a baseline. See [source-access direction](source-access-direction.md) for the bounded next experiment.
